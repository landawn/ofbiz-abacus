● Centralized Request/Response Logging in apache-ofbiz-framework

  ---
  Task: Modify the vendored Apache OFBiz codebase under ./apache-ofbiz-framework/ so every backend API request
  produces structured JSON request/response logs plus a curl reproduction line. The logging logic lives in exactly
  one place — not in any service, event handler, controller request entry, screen widget, or services*.xml.

  ---
  Scope: which requests must be logged

  Every HTTP request that hits OFBiz's ControlServlet (i.e., everything routed through any controller.xml
  <request-map>) — that's the surface every "API" in docs/api/api.md rides on. Concretely, requests landing at any
  webapp/*/control/* URL across all 16 OFBiz webapps (accounting, ap, ar, content, humanres, manufacturing,
  marketing, sfa, ordermgr, partymgr, catalog, facility, workeffort, webtools, commonext, ofbizsetup).

  Out of scope: static asset serving (*.ico, *.css, *.js, *.png, *.svg), the JMX/web-tools console pages that aren't
   routed through ControlServlet, and SOAP/XML-RPC endpoints that bypass the control servlet entirely. If a SOAP or
  other handler shares the same servlet, it's logged the same way.

  ---
  Output format

  Three pieces of information per request, emitted via OFBiz's existing log framework (which routes through SLF4J /
  Log4j 2 — use a dedicated logger name like org.apache.ofbiz.access).

  1. Request log (JSON):
  {
    "httpMethod": "POST",
    "requestPath": "/workeffort/control/DuplicateWorkEffort",
    "requestHttpHeaders": {"content-type": "application/json", "accept": "*/*", "...": "..."},
    "requestBody": "raw JSON body as a string (or empty for GET)"
  }
  2. Response log (JSON):
  {
    "httpStatus": 200,
    "requestPath": "/workeffort/control/DuplicateWorkEffort",
    "responseHttpHeaders": {"content-type": "application/json", "...": "..."},
    "responseBody": "raw JSON response body as a string"
  }
  3. curl reproduction line:
  curl -X POST 'http://<host>:<port>/workeffort/control/DuplicateWorkEffort' \
       -H 'content-type: application/json' \
       -H 'accept: */*' \
       --data-raw '{"workEffortId":"...","oldWorkEffortId":"..."}'
  3. Body (--data-raw) is omitted for GET. The scheme/host/port come from HttpServletRequest.getRequestURL() so the
  line is actually reproducible against the originating server.

  ---
  Mandatory architecture constraints

  - NO logging code in any service, screen, view, or request-event handler. Everything in services*.xml,
  controller.xml, and the applications/*/src/** business logic must remain untouched.
  - The logger must be implemented as a single cross-cutting component at the servlet layer. Pick whichever of the
  following fits cleanly:
    a. Servlet Filter registered in framework/webapp/.../web.xml (or in OFBiz's standard ofbiz-component.xml
  <webapp> <security-constraint>/<filter> slot). This is the canonical choice and the recommendation unless
  something else fits better.
    b. A javax.servlet.Filter packaged as a new tiny OFBiz module under
  framework/webapp/src/main/java/org/apache/ofbiz/webapp/access/, then declared once in the shared
  framework/webapp/config/common-controller.xml or equivalent so every webapp inherits it. This avoids editing 16
  individual web.xml files.
    c. Wrapping/replacing ControlServlet itself if a single subclass change is enough to put the logger in front of
  every request. Use only if the Filter route turns out infeasible.
  - All three log items (request, response, curl) must come out of the same component — not split across two
  filters.
  - Number of edited files should be as small as possible. A single new Java source plus, if necessary, one shared
  web.xml (or common-controller.xml) edit that all OFBiz webapps already pull in. Do not paste a <filter> block into
   16 separate web.xml files.

  If a single-place centralized solution turns out to be infeasible, do not silently introduce per-method or
  per-webapp duplications. Stop, explain the specific blocker, and ask before proceeding. Reasonable solutions
  almost always exist; the explanation should describe what was attempted and what specifically blocked the
  centralized approach.

  ---
  Implementation requirements

  - Body capture without breaking re-reads. Servlet streams can only be read once. Wrap HttpServletRequest and
  HttpServletResponse in caching wrappers (Spring's ContentCachingRequestWrapper/ContentCachingResponseWrapper if
  available on OFBiz's classpath; otherwise hand-rolled equivalents that buffer the bytes into a
  ByteArrayOutputStream). The downstream ControlServlet and all OFBiz events must still receive the body normally.
  - Header capture.
    - Include all request and response headers. Lowercase header names in the emitted JSON.
    - Do NOT redact any headers. authorization, cookie, set-cookie, proxy-authorization, x-api-key, and every other
  sensitive-looking header are logged in plain text with their real values. This is intentional — these logs exist
  for local API debugging/testing and need to be replayable as-is, which requires the real credentials in the curl
  line.
  - Body size guard. If the request or response body exceeds 64 KB, log "<elided: N bytes>" instead of the payload,
  to keep lines bounded.
  - Binary / non-text bodies. If content-type is not textual (e.g. application/octet-stream, image/*,
  application/pdf, multipart/*), emit "<binary: <content-type>, <N> bytes>".
  - Encoding. Decode body bytes using the request/response character set when available, otherwise UTF-8.
  - curl quoting. Single-quote the URL and headers. For the body use --data-raw with single quotes; escape any
  embedded ' as '\''. Strip headers the servlet container synthesizes that don't belong on a client request: host,
  content-length, connection. Since headers are not redacted, the generated curl line will include real
  Authorization: / Cookie: headers and is therefore directly replayable.
  - Skip noise. Don't log requests for static assets (*.ico, *.css, *.js, *.png, *.svg, *.woff*) or any path under
  /images/. Keep the skip rule a simple compile-time list in the filter source; no external config needed.
  - JSON serialization. Use Jackson (already on OFBiz's classpath through several modules). Do not introduce a new
  JSON library.
  - Performance hygiene. All logging work runs in the request thread — no async dispatch, no extra thread pool.
  Per-request overhead should be a few milliseconds for normal payloads.

  ---
  Log output destinations

  - Two sinks, both required:
    a. File: ./logs/apache-ofbiz-framework/api_yyyy_MM_dd.log — daily-rotated, UTF-8, append mode, one log event per
   line. Create the directory on startup if it doesn't exist. Path is relative to OFBiz's runtime working directory
  (typically the project root when launched via Gradle).
    b. Console (stdout) — same line format as the file.
  - Use OFBiz's existing Log4j 2 configuration mechanism rather than wiring an ad-hoc java.util.logging appender.
  Concretely:
    - Add one new logger named org.apache.ofbiz.access to OFBiz's Log4j 2 config
  (framework/start/src/main/resources/log4j2.xml or whichever log4j2.xml is the active one — locate before editing)
  with additivity="false".
    - Attach two appenders to it:
        - A RollingFile appender writing to ${sys:ofbiz.home}/logs/apache-ofbiz-framework/api_%d{yyyy_MM_dd}.log
  with daily rollover and %m%n pattern (the filter already emits a full JSON line, so the pattern should be just the
   message + newline — no timestamp prefix, no thread name, no level — so the file lines are pure JSON).
      - A Console appender with the same %m%n pattern routed to stdout.
  - Each call site emits two messages per request: one for the request, one for the response. The curl line is the
  third message. Each message is its own log event (its own line in the file and on stdout). All three carry the
  same correlation id (use MDC with key reqId set to a short random suffix or sequence number, so an aggregator can
  group them).

  ---
  Output / scope

  - Add: one new Java filter under a sensible OFBiz package, e.g.
  apache-ofbiz-framework/framework/webapp/src/main/java/org/apache/ofbiz/webapp/access/AccessLogFilter.java.
  - Edit: one web.xml (or the shared OFBiz controller include that registers framework-wide filters) so the filter
  applies to all webapps.
  - Edit: one log4j2.xml to add the org.apache.ofbiz.access logger and its two appenders.
  - Do not modify any controller, event class, service, screen, view, entity, or services*.xml.

  ---
  Verification

  After implementing:
  1. Restart OFBiz.
  2. Hit any controller-routed endpoint — e.g. POST /workeffort/control/createWorkEffort with a sample JSON body.
  3. Show:
    - The three log lines from the console (request JSON, response JSON, curl line) — all sharing the same reqId.
    - The same three lines appended to ./logs/apache-ofbiz-framework/api_<today>.log.
    - Confirmation via git status that no service / controller / services*.xml file was touched.

  If anything blocks a clean single-place solution (e.g. OFBiz's ControlServlet writes directly to the response in a
   way that prevents wrapping, or the active log4j2.xml location cannot be confidently identified), surface the
  blocker before proceeding.

● Mistakes I Made & Updated Prompt

  What went wrong

  Three distinct landmines that each ate a round-trip with you:

  Mistake 1 — Assumed Tomcat's "default web.xml" merge works for embedded contexts

  What I did: Declared <filter> + <filter-mapping> in framework/catalina/config/web.xml, the file passed to
  StandardContext.setDefaultWebXml(...), and assumed Tomcat would merge it into every webapp's effective web.xml.

  Why it was wrong: For programmatically-built StandardContexts (which is how OFBiz constructs them — new StandardContext() plus manual
  addLifecycleListener(new ContextConfig())), the default-web.xml merge does not reliably apply filter-mappings. The file IS read (the
  <session-config> next to my filter was honored), but my <filter-mapping> never landed in any webapp's filter chain.

  Should have done from the start: Register the filter programmatically via context.addFilterDef(...) + context.addFilterMapBefore(...) in
  CatalinaContainer.prepareContext(). That's the documented embedded-Tomcat pattern and works regardless of how the context is constructed.

  Mistake 2 — Cached the request body unconditionally, breaking form parameter parsing

  What I did: My CachingHttpServletRequest always pre-read getInputStream() into a byte buffer so the body could be logged.

  Why it was wrong: Tomcat parses application/x-www-form-urlencoded (and multipart/*) body parameters lazily, on the first
  request.getParameter("...") call. By draining the stream first, I left Tomcat with nothing to parse — so LoginWorker's call to
  request.getParameter("USERNAME") returned empty, and login broke for every user.

  Should have done from the start: Branch on Content-Type at the very top of the caching wrapper. For form/multipart, leave the stream
  untouched and reconstruct the body for logging from getParameterMap(). Cache the raw stream only for JSON/XML/text content types.

  Mistake 3 — Used SLF4J's LoggerFactory without verifying a binding exists

  What I did: Coded the filter with org.slf4j.Logger + org.slf4j.LoggerFactory.getLogger("org.apache.ofbiz.access"), assuming
  SLF4J-on-the-classpath meant it was wired to Log4j.

  Why it was wrong: OFBiz ships slf4j-api 2.x but only the legacy log4j-slf4j-impl 1.7.x binding (StaticLoggerBinder-based). SLF4J 2.x looks
   for ServiceLoader providers, doesn't find one, prints "No SLF4J providers were found. Defaulting to no-operation (NOP) logger
  implementation" at startup, and every LOG.info(...) call silently becomes a no-op. The empty log directory existed only because Log4j
  eagerly creates the appender file's parent when the config loads; nothing ever wrote to it.

  Should have done from the start: When working inside a host application, check LoggerFactory's startup output for binding warnings. For
  OFBiz specifically, use org.apache.logging.log4j.LogManager.getLogger(...) directly (and ThreadContext for MDC) — bypass SLF4J entirely.

  Mistake 4 (minor) — Used path relative to the wrong working directory

  What I did: Configured the Log4j appender path as logs/apache-ofbiz-framework/api_...log.

  Why it was wrong: OFBiz launches with cwd = apache-ofbiz-framework/, but you wanted the log under the parent ofbiz-abacus/logs/.... The
  path needed a ../ prefix.

  Should have done from the start: Identify the JVM working directory before picking a relative path, or use an absolute path keyed off a
  known system property.
