  ---
  Source of behavior

  For each method, read the Javadoc tag service: <name>  entities: <list>  auth: <true|false> and trace:

  1. Service definition — find <service name="<name>"> in the controller's OFBiz component's servicedef/services*.xml (mapping established
  in CONTROLLERS registry of scripts/gen_controller_dtos.py; Commonext follows CROSS_COMPONENT_OWNERS in scripts/wire_controller_dtos.py).
  Capture engine, location, invoke, permission-service, IN/OUT attributes.
  2. Service implementation:
    - engine="java" → FQCN under apache-ofbiz-framework/.../src/main/java/...
    - engine="groovy" → .groovy under .../src/main/groovy/...
    - engine="simple" → MiniLang <simple-method> under .../minilang/.../*.xml
    - engine="entity-auto" → trivial CRUD on default-entity-name
    - engine="group" → invoke each service in service_groups.xml in order
  3. ECA chain — entries in secas.xml with service="<name>" that fire on commit. Implement them in-line in the service method (audit logs,
  status side-effects, downstream calls).
  4. Permission service — for every <permission-service service-name="X" main-action="Y"/> in the service def, call
  SecurityService.hasEntityPermission(...) per the existing WorkeffortService.checkPermission(...) pattern. Anonymous (no userLoginId)
  callers pass in dev. Permission failures throw PermissionDeniedException (already wired to HTTP 403).
  5. No-DTO endpoints (the 371 left as Map<String, Object> by the wiring script — no <service> matched the Javadoc tag): drive the
  implementation from the OFBiz controller.xml entry instead. Open
  apache-ofbiz-framework/{applications,framework}/{component}/webapp/{component}/WEB-INF/controller.xml, find the <request-map uri="...">
  whose URL matches the controller's @*Mapping(...), then implement the <event> it points at (a class method, a groovy script, or a screen
  action) — same source-engine rules as steps 2-3. Keep the method signature Map<String, Object> since no DTO exists. Add // (no service def
   — ported from controller.xml event handler) to the Javadoc.

  ---
  Architecture — one service class per OFBiz subdomain

  Mirroring how OFBiz splits its own service definitions across multiple services_*.xml files, split each controller's service layer along
  the same boundaries:

  - Package: com.landawn.ofbiz.service
  - One service class per OFBiz servicedef/services*.xml file the controller pulls from. Examples:
    - ProductController (which pulls from services_product.xml, services_category.xml, services_store.xml, services_facility.xml,
  services_price.xml, services_feature.xml, etc.) → ProductService, ProductCategoryService, ProductStoreService, ProductFacilityService,
  ProductPriceService, ProductFeatureService, …
    - AccountingController → AcctgTransService, InvoiceService, PaymentService, BillingAccountService, FinAccountService, etc.
    - Small components (Marketing, Commonext, Humanres) may collapse into a single service class.
  - The controller injects whichever services it needs and delegates each method to one of them.
  - Cross-controller reuse is allowed: CommonextController already imports DTOs from model.party, model.product, etc.; the corresponding
  services (PartyGroupService, ProductStoreService) are the same beans, not duplicates.
  - Aim to keep each service class under ~2,000 lines. If one file exceeds that, split further along the OFBiz boundary (rarely a
  services_xxx_yyy.xml sub-split exists; use it).

  For Workeffort: WorkeffortService stays as-is (one file, ~945 lines — under the threshold).

  ---
  Library priority (strict)

  Tier 1 — abacus-common, abacus-jdbc, abacus-query. Default to these:
  - Utilities: com.landawn.abacus.util.N, Strings, Numbers, IOUtil, DateUtil, Maps, Beans
  - JSON / XML: N.toJson, N.fromJson, N.toXml, N.fromXml
  - DAO calls: built-in CrudDao (get, gett, insert, update, delete, list, stream, exists, count); join navigation via
  CrudJoinEntityHelper.loadJoinEntities(entity, FieldType.class)
  - Custom queries: @Query from com.landawn.abacus.jdbc.annotation on DAO methods
  - Conditions: com.landawn.abacus.query.condition.* (Filters, Criteria)

  Tier 2 — Spring Boot. Only for HTTP binding (@RestController, @RequestBody, @RequestParam), @Transactional, dependency injection,
  validation annotations.

  Tier 3 — Apache Commons. Only when neither Tier 1 nor Spring covers it. Never import org.apache.commons.* directly outside
  com.landawn.ofbiz.util.apache.*. Instead:
  - Add (or extend) a delegation class under com.landawn.ofbiz.util.apache named after the source library: CommonsLang, CommonsCodec,
  CommonsIo, CommonsCollections, etc.
  - Expose the needed function as public static, delegating to the Apache method, with a one-line Javadoc pointing at the underlying call.
  - Application code calls only the delegation class.
  - If abacus already provides an equivalent (e.g. Strings.isBlank vs StringUtils.isBlank), prefer abacus — no delegation needed.

  ---
  DAO usage

  - Default to built-in CrudDao methods for single-entity CRUD, PK lookup, list(Condition), count(Condition), delete(Condition).
  - For FK navigation in returned payloads: every relevant DAO already extends CrudJoinEntityHelper — use loadJoinEntities(entity,
  Type.class), not manual JOIN SQL.
  - For multi-table joins, aggregations, or anything Condition can't express: add an @Query("SELECT ...") method on the relevant DAO
  interface. Follow @Query's parameter-binding rules (@Bind, positional ?, named :param).
  - Transactions: @Transactional (Spring) on the service method, never on the DAO.

  ---
  Input handling

  - Endpoints already wired to typed DTOs (@RequestBody XxxRequest request): use request.getXxx() getters; convert to Map<String, Object>
  via ServiceInput.toMap(request) at the boundary if internal logic uses maps (same pattern as WorkeffortService.createWorkEffort).
  - Endpoints left as Map<String, Object> body or Map<String, String> params: trust the inbound map — no explicit optional="false"
  validation, no type-coercion shims. DAO failures bubble up to Spring's default 500.
  - Generated IDs: use SequenceUtil.next() (16-char timestamp+random) where OFBiz uses delegator.getNextSeqId(...). Echo the minted ID in
  the response under the same key OFBiz returns.
  - Timestamps: Timestamp.from(Instant.now().truncatedTo(ChronoUnit.MILLIS)) (matches WorkeffortService.nowTs() — millisecond precision
  intentionally; nanoseconds break composite-PK round-tripping).

  ---
  Response envelope (typed-DTO endpoints)

  Service methods return XxxResponse (already typed). Use the helpers in ServiceResponse:
  - Success: ServiceResponse.ok(XxxResponse::new), then set OUT fields.
  - Error: ServiceResponse.error("message", XxxResponse::new).
  - Service-to-service composition: ServiceInput.narrow(parent, ChildRequest::new) to project; ServiceResponse.errorOf(childResp,
  ParentResponse::new) to propagate errors across response types.

  The controller's wrap() helper (already added by wire_controller_dtos.py) routes 200/400 based on ServiceResponse.isError(dto).

  For the 371 Map-shaped endpoints: return ResponseEntity<Map<String, Object>> directly using the existing ServiceResponse.success(...) /
  error(...) map builders.

  that controller, and the response DTO will carry the new fields.
