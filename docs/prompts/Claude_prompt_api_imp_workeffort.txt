  ---
  Response shape parity

  OFBiz returns one of three shapes per request, and the access log shows which:

  - HTML view (most browser-driven endpoints, e.g. <response type="view" value="someScreen"/>): OFBiz returns Content-Type: text/html with a
   rendered screen. The Spring port does NOT replicate the HTML. It returns ResponseEntity.ok(Map<String, Object>) containing the service's
  OUT attributes plus any field the OFBiz screen would have populated (most importantly the newly-created/updated entity's primary key —
  e.g., workEffortId, timesheetId, timeEntryId, etc.). Document this in the controller method's Javadoc.
  - JSON event response (AJAX-style endpoints like *Json request URIs): Content-Type: application/json. The Spring port must produce a JSON
  body whose top-level keys match exactly what OFBiz returns.
  - Redirect (3xx with Location: header): the Spring port returns a JSON envelope of the redirect target — e.g.,
  {"redirectTo":"/workeffort/control/ViewWorkEffort?workEffortId=10042","responseMessage":"success"} — not an HTTP 302.

  For error paths, OFBiz returns result is [error] with a flash message map. The Spring port returns HTTP 400 with the OFBiz error envelope
  plus the offending condition:
  {"responseMessage":"error","errorMessage":"<message>","errorMessageList":["..."]}
  and matches the OFBiz error condition (e.g., missing required attribute, status-change-not-valid, permission-denied).

  ---
  OFBiz "result" envelope — included for parity

  Every successful response wraps the OUT attributes in OFBiz's conventional envelope keys:
  {
    "responseMessage": "success",
    "successMessage": "<optional human-readable success message if the OFBiz service set one>",
    "<out-attr-1>": "...",
    "<out-attr-2>": "...",
    ...
  }
  Every error response uses:
  {
    "responseMessage": "error",
    "errorMessage": "<single-line message>",
    "errorMessageList": ["...", "..."]
  }
  For services that fail validation (error) the HTTP status is 400; for services that succeed-with-warnings (fail) it's 200 with
  "responseMessage":"fail"; for clean success it's 200 with "responseMessage":"success". Permission denials surface as HTTP 403 via
  PermissionDeniedException (already wired).
