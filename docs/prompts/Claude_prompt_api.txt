  ---
  Task: Inventory every backend web service and REST endpoint defined under ./apache-ofbiz-framework/, document them in ./docs/api/api.md, and scaffold matching empty Spring Boot controller classes under com.landawn.ofbiz.controller.

  ---
  Inputs to scan

  Under ./apache-ofbiz-framework/, collect API surface from these OFBiz mechanisms (skip none unless explicitly excluded below):

  1. REST endpoints — *.rest.xml configuration files, RestServlet-mounted resources, and any Jakarta/Jersey @Path annotations in .java files.
  2. SOAP/XML-RPC/HTTP service exports — entries in services*.xml whose <service> has export="true" (these are publicly callable over webtools/control/SOAPService, xmlrpc, httpService).
  3. Webapp controller.xml request maps — <request-map uri="..."> entries, especially those with <event type="service" ...> (these invoke services via HTTP) or <event type="java" ...>. Include the auth attribute (auth="true|false") and
  the HTTP method if specified.
  4. Service definitions (services*.xml) referenced by any of the above — capture the service name, engine (java, groovy, simple, entity-auto), location, and invoke method so the implementation class is named in the doc.

  For each API, trace the call chain through three layers:

  - Controller/Handler layer — the OFBiz request handler or REST resource class (e.g. org.apache.ofbiz.webapp.event.ServiceEventHandler, a Jersey resource, or the controller.xml request entry itself). Tag with auth=true|false where the
  source declares it.
  - Service layer — the Java/Groovy class + method that implements the service (<service location="..." invoke="..."/>). For engine="groovy" or engine="simple" (MiniLang) services, list the script path (e.g.
  component://party/groovyScripts/party/CreateParty.groovy or component://party/minilang/party/PartyServices.xml#createParty).
  - Persistence layer — the entity/entities the service reads or writes, listed by OFBiz entity name (e.g. Party, ProductPrice). Best-effort extraction:
    - <entity-one entity-name="X"/> and similar in MiniLang
    - EntityQuery.use(...).from("X"), delegator.findOne("X", ...), delegator.create("X", ...), delegator.store(...), etc. in Java/Groovy
    - If not statically determinable, list as unknown.

  Skip:
  - Pure view-only request-map entries (no <event>, only <response type="view" .../> — these are page renders, not APIs).
  - Static asset handlers.
  - Test/fixture components under framework/base/src/test/**.

  ---
  Output 1 — ./docs/api/api.md

  A single Markdown file with one section per OFBiz component (alphabetical), each containing a three-column table:

  | Path | Implementation chain (Controller → Service → Persistence) | Description |

  Column rules:

  - Path — the URL the client calls. Forms:
    - REST: GET /rest/products/{id} (include HTTP method)
    - controller.xml request: POST /accounting/control/createInvoice (include the webapp mount + control servlet path + request URI)
    - SOAP service export: POST /webtools/control/SOAPService  [service=createParty] (service name as a tag)
  - Implementation chain — three segments joined by →:
    a. Controller/handler class (FQCN) or the controller.xml-mounted servlet, suffixed with [auth=true|false].
    b. Service name + implementation. For Java services: createParty → org.apache.ofbiz.party.party.PartyServices#createParty. For Groovy/MiniLang services: createParty → component://party/groovyScripts/.../CreateParty.groovy or
  component://.../PartyServices.xml#createParty.
    c. Touched entities by OFBiz entity name, comma-separated (Party, PartyType, PartyStatus). No Java type references. unknown when not statically derivable.
  - Description — first non-empty <description> from the service definition, or the controller.xml <request-map> description, or — if absent.

  File header should include: total API count, breakdown by component, and the date this was scanned. Also list the source files consulted (path + count).

  Order tables by URL within each component for stable diffs.

  ---
  Output 2 — Controller scaffolds under com.landawn.ofbiz.controller

  For each component that exports at least one API, generate one Spring @RestController class per component (grouping by component, not per endpoint, keeps the file count manageable and matches how OFBiz organizes services):

  - Class name: {ComponentPascalCase}Controller (e.g. accounting → AccountingController, party → PartyController).
  - Package: com.landawn.ofbiz.controller.
  - Annotation: @RestController + @RequestMapping("/{component-lowercase}") (e.g. /accounting).
  - One method per unique URI. If the same service backs two different URIs, generate two methods. If two URIs collide on the derived method name, suffix the duplicates with the URI's last path segment (camelCase) to disambiguate.
  - Method naming: camelCase derived from the service name, or from the URI's last segment if no service is invoked.
  - Method annotation: appropriate @GetMapping / @PostMapping / etc. with the path relative to the class-level @RequestMapping (so the full path matches OFBiz's URL).
  - Method signature:
    - Path params → @PathVariable
    - Query params → @RequestParam (best-effort from the service's <attribute mode="IN" .../> definitions)
    - Body params (for POST/PUT) → a single @RequestBody Map<String, Object> (OFBiz services are loosely typed; a Map keeps the scaffold honest)
    - Return type → ResponseEntity<Map<String, Object>>
  - Method body — exactly:
  // TODO
  throw new UnsupportedOperationException();
  - Javadoc above each method:
    - One-line description from the API doc
    - // service: {serviceName}  entities: {entities}  auth: {true|false} so a maintainer can find the OFBiz original

  Imports: Spring (org.springframework.web.bind.annotation.*, org.springframework.http.ResponseEntity) and java.util.Map. No Lombok.

  Do not generate one controller per endpoint — group by OFBiz component.

  ---
  Approach

  Write a Python script scripts/gen_api_inventory.py that:

  1. Walks apache-ofbiz-framework/ once. Parses:
    - All controller.xml files (locating webapp mounts via the containing ofbiz-component.xml + WEB-INF directory).
    - All services*.xml (build a serviceName → {engine, class-or-script, method, description, IN-attrs, touched-entities} map).
    - All *.rest.xml and any @Path-annotated .java files.
  2. Joins request-maps to services by <event invoke="serviceName"/>.
  3. Best-effort entity extraction (greps + regex on the service's implementing file/script). Results go into api.md as OFBiz entity names.
  4. Writes docs/api/api.md.
  5. Writes one controller per component to src/main/java/com/landawn/ofbiz/controller/.
  6. Prints a summary: components processed, APIs found per layer (REST / SOAP-export / controller.xml-service / controller.xml-java), controllers written, methods written.

  Re-runnable: the script always overwrites both api.md and the controller classes (idempotent).

  ---
  Confirmed answers carried into this prompt

  1. Auth gating — include all APIs (both auth=true and auth=false); record the flag in the doc and as a // auth: … tag in each method's Javadoc.
  2. Method-per-URI — one controller method per unique URI; collisions on derived method names get a suffix from the URI's last segment.
  3. Entity references in api.md — original OFBiz entity names, no Java type references. Controllers don't reference entities at all (they throw).
  4. Groovy / MiniLang services — list the script path as the "implementation."
